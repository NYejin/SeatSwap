# SeatSwap 작업일지

## 2026-10-08

### 결정 (CLAUDE.md '확정 전 기본안'에 대한 사용자 답변을 확정으로 반영)
1. **구역·좌석 단위**: 공연장 단위 구역 테이블을 두지 않는다. 공연마다 공연장 좌석을 그대로 쓰기도 바꿔 쓰기도 하므로 **공연 단위로 좌석**을 둔다. 구역 등록·자동완성은 좌석표 기능이 추가될 때 신경 쓸 부분이며, 지금은 사용자가 구역·열·번을 **텍스트로 직접 입력**한다. 공연장 관련 새 지시가 나오면 사용자에게 되묻는다
2. **열 표기**(숫자/문자)는 사용자에게 입력받는다
3. 직사각형 범위 선택 같은 고급 범위 입력과 펼침 상한 등은 좌석표 기능이 추가될 때 신경 쓸 부분(지금은 단순 텍스트 입력)
4. **회차**: 교환은 같은 공연 안에서 회차 구분 없이 가능, 매칭은 사용자가 원하는 회차끼리만(희망 회차 지정)
5. **추가금**: 상한 없음. 입력칸 대신 체크박스 [추가금 없음] [제시] (제시를 고를 때만 금액 입력)
6. **흐름**: 매칭 → 채팅 → 교환 후 각자 수락 → 교환 확정/완료
7. **교환 성사 후**: 마이페이지에 DB 기록만 남기고 관련 기능은 따로 추가하지 않는다. 사용자 신고 기능만 추후 추가
8. **같은 좌석 중복 등록**: 같은 회차·구역·열·번의 활성 티켓은 1개만 허용, 사용자당 활성 티켓 수 상한(예 20). 이미 등록된 좌석이면 안내 팝업/말풍선 + '내 티켓 인증' 링크. 인증 방식은 추후 결정(사진 업로드 → 관리자 수동 확인 예정)
9. **후보 노출**: 사용자가 교환을 원하는 회차를 우선, 회차 우선순위는 사용자가 설정
10. **범위 제한 없음**: 지정석·1매 제한을 두지 않는다(스탠딩 등도 텍스트 입력). 연석·3자 이상 순환 교환은 데이터 모델이 막지 않게 한다
11. **후기·신뢰도·신고**: 후기 기능은 만들지 않는다. 사용자 신고는 필수(교환 핵심 흐름 이후). 신뢰도 점수는 매칭에 쓰지 않고, 매칭 우선순위는 신뢰도가 아니라 사용자가 정한 우선순위를 따른다
- 이전 기본안 중 폐기된 것: 구역 자동완성, 요청당 300석 펼침 상한, 지정석·1매만, '후기·신뢰도 우선'
- CLAUDE.md '좌석표 트랙 동결' 항목에 "구역 등록·자동완성·범위 선택 UI는 좌석표 기능과 함께 후속" 추가

## 공연장 테이블 삭제(4차 답변)

### 결정 (사용자 4차 확정, 2026-10-08)
1. **venue 테이블 삭제를 구현했다**(미커밋, `feature/remove-venue`). 공연장은 `performance.venue_name VARCHAR(100) NOT NULL` 텍스트다. 공백 정리 후 1~100자이고 전각 통일·중복 판정은 하지 않는다.
2. 공연 목록 검색은 **제목만**. `GET /api/venues`·`POST /api/venues`는 삭제했다.
3. **공연장 이름은 등록 후 수정할 수 없다.** 티켓팅 링크를 등록하면 공연 정보를 자동으로 읽어올 예정이라 수정이 필요 없고, 공연 진행 측 사정으로 공연장·회차·날짜가 바뀌면 사용자가 **관리자에게 수정 제안**을 한다(관리자 기능은 후속).
4. 등록 화면은 **3단계**: ①티켓팅 링크(중복 확인) ②공연 정보(제목·공연장 이름·회차, 지금은 직접 입력) ③확인·등록. 링크를 입력하면 다음 단계에 공연 이름·공연장·회차 등을 한꺼번에 미리 채워 '이 정보가 맞나요?'를 묻고, 아니면 직접 수정 후 등록하는 **자동 입력은 다음 작업(미구현)**.

### 구현 요약 (코드 에이전트 작업을 문서로 기록)
- 백엔드: V2(`V2__drop_venue_use_venue_name.sql`)가 프로시저 가드로 각 단계의 적용 여부를 확인하며(재실행 가능) `venue_name`을 추가해 venue 이름을 백필하고, 백필 실패 행이 있으면 SIGNAL로 중단한 뒤 `venue_id`·FK·venue 테이블을 삭제한다. Venue 엔티티·컨트롤러·서비스·저장소·DTO·테스트를 삭제했고 응답은 `venueName`, 요청의 400 필드 오류 키는 `venueName`이다. 공연 수정(PATCH)은 title만 받고 venueName/venueId가 와도 무시한다.

## 교환 규칙 확정(6차 답변)

### 결정 (사용자 6차 확정, 2026-10-08)
1. **추가금 판정**: 유형 4종 X(추가금 X, 지불 안 함) / ANY(상관없음) / POS(>0, 받아야만 교환) / NEG(<0, 낼 의향). 금액은 계산에 쓰지 않고 **유형만** 본다. **POS-POS 불성립, POS-X 불성립, 나머지 성립.** X-X와 NEG-NEG는 사용자가 명시하지 않아 기본값 '성립'(확인 필요). 금액은 후보 목록에 참고용으로 표시한다. 부호는 +가 내가 받을 금액, -가 내가 낼 수 있는 금액. 입력 UI는 [추가금 X]/[상관없음]에 더해 금액 부호 입력.

## 교환 희망 조건 등록 구현 (브랜치 `feature/exchange-want`, 미커밋)

### 구현 사실
- Flyway `V4__exchange_want_tables.sql`: `exchange_request`(티켓당 1개), `exchange_want_range`(입력한 범위, 수정 화면 복원용), `exchange_want_seat`(펼친 좌석), `exchange_want_session`(희망 회차+우선순위) 4개 테이블. 매칭·잠금·채팅·이력·차단은 미구현(V5 이후).
- API: `POST /api/exchange/requests {ticketId, extraType(X/ANY/POS/NEG), extraAmount, wantSessions[{sessionId,priority}], ranges[{zone,rowFrom,rowTo,colFrom,colTo}]}`, `GET /api/exchange/requests/me`, `PATCH/DELETE /api/exchange/requests/{id}`.
- 서버 안전 상한 5,000석·50범위(`exchange.want.*`), 초과 시 422 `WANT_SEAT_LIMIT_EXCEEDED`/`WANT_RANGE_LIMIT_EXCEEDED`(count/limit 포함). 겹침은 합집합 허용, 문자 열은 하나씩, 자기 좌석 포함 422는 희망 회차가 내 티켓 회차 하나뿐일 때만(다른 회차가 하나라도 있으면 같은 위치도 허용), 티켓당 요청 1개 409 `REQUEST_ALREADY_EXISTS`, 남의 요청·티켓 403(없는 id 404), 추가금은 요청 단위.
- **티켓 내리기 동작 추가**: 티켓을 내리면 해당 요청이 CLOSED로 바뀌고 이후 수정은 422 `TICKET_NOT_ACTIVE`. 예약 잠금 409는 매칭 구현 때 `ensureCanDeactivate`/`ensureNoActiveProposal` 훅에서 추가하며, 'PATCH/DELETE 진행 중 제안 409'도 훅만 있고 미구현이다.
- 백엔드 테스트 254건(리뷰 반영 후), 5,000석 POST 약 156ms.

### 리뷰 반영 (구현 사실 변경)
- '같은 자리의 다른 회차 교환' 한계는 해소: 자기 좌석 포함 422 `WANT_INCLUDES_OWN_SEAT`는 희망 회차가 내 티켓 회차 하나뿐일 때만, 다른 회차가 하나라도 있으면 같은 위치도 허용(사용자가 별도 결정 없이 추천안 채택, 이의 시 변경 가능).
- 펼침 상한 판정은 겹침 포함 합이 아니라 합집합 기준이며, 응답 `count`와 `wantSeatCount`의 의미가 같다.
- 지난 회차 마감 정책을 요청에도 적용: 내 티켓 회차 마감이면 422 `SESSION_CLOSED`, 희망 회차가 마감이면 400 `wantSessions[i].sessionId`.
- 열·번의 부호 붙은 정수형(`-3`, `+3`, U+2212)은 400 거부(티켓·희망 범위 공통).
- 잠금 순서 규약: 항상 티켓→요청, 요청만 잠그는 update/delete 경로에서 티켓 잠금 금지.

### 알려진 한계 (1건)

## 매칭 후보 조회 구현 (브랜치 `feature/exchange-candidates`, 미커밋)

### 구현 사실

## 제안·수락(매칭·예약) 구현 (브랜치 `feature/exchange-propose-accept`, 미커밋)

### 결정 경위
- 사용자 결정(2026-10-08, 명령 6): 요청당 '제안 1개 -> 수락' 모델 대신, 이미 확정한 흐름(후보 선택 -> 채팅 여러 개 동시 -> 양쪽 예약 -> 각자 완료)에 매핑해 구현한다.

### 구현 사실
- Flyway `V5__exchange_match_tables.sql`: `exchange_match`·`exchange_ticket_lock` 2개 테이블만 만든다(현재 10개 테이블). `user_block`·`chat_message`·`exchange_history`는 V6 이후.
- API:
  - `POST /api/exchange/requests/{id}/proposals {targetRequestId}`: 매칭을 CHATTING으로 생성(한 요청에 여러 개 동시 가능, 같은 쌍의 열린 매칭은 1개). 후보 재검증 실패 422 `NOT_A_CANDIDATE` 등, 같은 쌍 열린 매칭 409 `MATCH_ALREADY_OPEN`.
  - `POST /api/exchange/matches/{id}/accept`: 호출자 쪽 예약 동의. 양쪽이 누르면 RESERVED + 두 티켓 `exchange_ticket_lock`을 한 트랜잭션에서 INSERT. 다른 매칭에서 이미 잠겼으면 409 `TICKET_ALREADY_RESERVED`, 이미 눌렀으면 멱등 200.
  - `POST /api/exchange/matches/{id}/reject`(제안받은 b측만)·`/cancel`(참여자 누구나): CANCELED(`canceled_by_id`, 시스템 취소=NULL), RESERVED였으면 잠금 해제. 취소 후 같은 쌍 재매칭 허용(재매칭 불가는 차단·신고에만). 불허 전이 409 `MATCH_STATE_CONFLICT`.
- 훅 채움: 열린 매칭(CHATTING/RESERVED)이 있으면 요청 PATCH/DELETE 409 `ACTIVE_MATCH_EXISTS`; 잠긴 티켓 내리기 409 `TICKET_RESERVED`(잠기지 않았으면 요청 CLOSED + 그 티켓의 CHATTING 매칭 시스템 취소); 후보 조회에서 예약 잠금 티켓·같은 쌍 열린 매칭 제외, 내 티켓이 잠겨 있으면 후보 조회 422 `TICKET_LOCKED`(차단 제외는 `user_block`이 없어 여전히 미적용); 요청 삭제 시 CANCELED 매칭 행을 먼저 삭제, COMPLETED가 있으면 409 `MATCH_HISTORY_EXISTS`.
- 범위 밖: COMPLETED·채팅·교환 이력·차단·매칭 조회/목록 API.
- 규칙: 티켓 좌석·회차 갱신은 COMPLETED 시점에 한 트랜잭션에서 두 티켓을 교체한다(양쪽 완료 순간, 설계 확정 g). 이미 시작한 채팅의 accept에는 회차 마감 검사를 하지 않는다(공연 시작 후에도 예약·취소 가능, 확정). 잠금 순서는 티켓 id 오름차순 -> 요청 id 오름차순 -> 매칭.
- 교훈: FK에 쓰이는 인덱스에 갱신 컬럼(status 등)을 붙이면 UPDATE가 부모 행에 S 잠금을 걸어 교착이 났다(실제 재현). `idx_exchange_match_user_a/b`를 (user_x_id, status)에서 단일 컬럼으로 바꿔 해결했다.
- 검증: 기본 테스트 384건 중 341 실행·43 skip·실패 0, 환경변수 포함 401건 통과. 동시성 HTTP 50라운드 x 4 시나리오에서 불변식 위반 0, 서버 로그 교착 0.

## 범위별 추가금·요청 소프트 삭제 (브랜치 `feature/range-extra`, 7차 답변 2026-10-08~09, 미커밋)

(2026-10-09에 문서를 동기화했으나 날짜별 파일을 새로 만들지 않고 같은 작업 흐름으로 이 파일에 이어 적는다.)

### 사용자 확정 (7차 답변)
1. 추가금은 요청 단위가 아니라 **희망 범위 단위**다. 한 티켓에서 1열은 낼 의향, 5열은 추가금 X, 10열은 받아야 교환처럼 범위마다 다르다(범위-추가금 짝).
2. 겹치는 범위에서 유형·금액이 다르면 422 `WANT_EXTRA_CONFLICT`로 거부한다(완전히 같은 겹침만 허용). 응답 최상위에 `conflicts:[[i,j]]`.
3. **요청 소프트 삭제**: 상태 DELETED, `deleted_at`. 삭제 후 같은 티켓에 새 요청을 만들 수 있다. 삭제 시 want_range/seat/session 삭제. 삭제된 요청은 후보·수정·`/requests/me`에서 제외하고 내 매칭 목록에는 회색 '(삭제)'로 표시. 삭제된 요청의 수정·후보 조회는 409 `REQUEST_DELETED`, 삭제 API는 멱등 204.
4. `exchange_match`에 추가금 스냅샷 4컬럼(`a/b_extra_type`, `a/b_extra_amount`).
5. 요청 수정·삭제 시 CHATTING 매칭은 시스템 취소(`canceled_by` NULL), RESERVED가 있으면 409 `ACTIVE_MATCH_EXISTS`('예약된 매칭이 있어…'), 완료된 매칭이 있어도 삭제 허용(`MATCH_HISTORY_EXISTS` 제거; 지금은 COMPLETED 기능 없음).
6. **X–X·NEG–NEG는 성립으로 확정**('확인 필요' 항목 해소).
7. 미삭제 요청만 티켓당 1개(`uk_exchange_request_live_ticket`, 생성 컬럼 `live_flag`).
8. 이전 서술 정정: '요청 삭제 정책·낯선 제안 문제'는 결정 완료(소프트 삭제, 채팅 자동 취소 후 수정 허용).

### 구현 사실
- Flyway V6(`V6__exchange_extra_per_range.sql`)·V7(`V7__exchange_request_soft_delete.sql`), 재실행 가능 프로시저 패턴. **현재 DB V1~V7, 10개 테이블(테이블 수 불변)**. 차단·채팅·이력 테이블은 **V8 이후**.
