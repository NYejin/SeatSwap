# SeatSwap 작업일지

## 2026-10-08

### 결정 (CLAUDE.md '확정 전 기본안'에 대한 사용자 답변을 확정으로 반영)
1. **구역·좌석 단위**: 공연장 단위 구역 테이블을 두지 않는다. 공연마다 공연장 좌석을 그대로 쓰기도 바꿔 쓰기도 하므로 **공연 단위로 좌석**을 둔다. 구역 등록·자동완성은 좌석표 기능이 추가될 때 신경 쓸 부분이며, 지금은 사용자가 구역·열·번을 **텍스트로 직접 입력**한다. 공연장 관련 새 지시가 나오면 사용자에게 되묻는다
2. **열 표기**(숫자/문자)는 사용자에게 입력받는다
3. 직사각형 범위 선택 같은 고급 범위 입력과 펼침 상한 등은 좌석표 기능이 추가될 때 신경 쓸 부분(지금은 단순 텍스트 입력)
4. **회차**: 교환은 같은 공연 안에서 회차 구분 없이 가능, 매칭은 사용자가 원하는 회차끼리만(희망 회차 지정)
5. **추가금**: 상한 없음. 입력칸 대신 체크박스 [추가금 없음] [제시] (제시를 고를 때만 금액 입력)
6. **흐름**: 매칭 → 채팅 → 교환 후 각자 수락 → 교환 확정/완료
7. **교환 성사 후**: 마이페이지에 DB 기록만 남기고 관련 기능은 따로 추가하지 않는다. 사용자 신고 기능만 추후 추가
8. **같은 좌석 중복 등록**: 같은 회차·구역·열·번의 활성 티켓은 1개만 허용, 사용자당 활성 티켓 수 상한(예 20). 이미 등록된 좌석이면 안내 팝업/말풍선 + '내 티켓 인증' 링크. 인증 방식은 추후 결정(사진 업로드 → 관리자 수동 확인 예정)
9. **후보 노출**: 사용자가 교환을 원하는 회차를 우선, 회차 우선순위는 사용자가 설정
10. **범위 제한 없음**: 지정석·1매 제한을 두지 않는다(스탠딩 등도 텍스트 입력). 연석·3자 이상 순환 교환은 데이터 모델이 막지 않게 한다
11. **후기·신뢰도·신고**: 후기 기능은 만들지 않는다. 사용자 신고는 필수(교환 핵심 흐름 이후). 신뢰도 점수는 매칭에 쓰지 않고, 매칭 우선순위는 신뢰도가 아니라 사용자가 정한 우선순위를 따른다
- 이전 기본안 중 폐기된 것: 구역 자동완성, 요청당 300석 펼침 상한, 지정석·1매만, '후기·신뢰도 우선'
- CLAUDE.md '좌석표 트랙 동결' 항목에 "구역 등록·자동완성·범위 선택 UI는 좌석표 기능과 함께 후속" 추가

## 공연장 테이블 삭제(4차 답변)

### 결정 (사용자 4차 확정, 2026-10-08)
1. **venue 테이블 삭제를 구현했다**(미커밋, `feature/remove-venue`). 공연장은 `performance.venue_name VARCHAR(100) NOT NULL` 텍스트다. 공백 정리 후 1~100자이고 전각 통일·중복 판정은 하지 않는다.
2. 공연 목록 검색은 **제목만**. `GET /api/venues`·`POST /api/venues`는 삭제했다.
3. **공연장 이름은 등록 후 수정할 수 없다.** 티켓팅 링크를 등록하면 공연 정보를 자동으로 읽어올 예정이라 수정이 필요 없고, 공연 진행 측 사정으로 공연장·회차·날짜가 바뀌면 사용자가 **관리자에게 수정 제안**을 한다(관리자 기능은 후속).
4. 등록 화면은 **3단계**: ①티켓팅 링크(중복 확인) ②공연 정보(제목·공연장 이름·회차, 지금은 직접 입력) ③확인·등록. 링크를 입력하면 다음 단계에 공연 이름·공연장·회차 등을 한꺼번에 미리 채워 '이 정보가 맞나요?'를 묻고, 아니면 직접 수정 후 등록하는 **자동 입력은 다음 작업(미구현)**.

### 구현 요약 (코드 에이전트 작업을 문서로 기록)
- 백엔드: V2(`V2__drop_venue_use_venue_name.sql`)가 프로시저 가드로 각 단계의 적용 여부를 확인하며(재실행 가능) `venue_name`을 추가해 venue 이름을 백필하고, 백필 실패 행이 있으면 SIGNAL로 중단한 뒤 `venue_id`·FK·venue 테이블을 삭제한다. Venue 엔티티·컨트롤러·서비스·저장소·DTO·테스트를 삭제했고 응답은 `venueName`, 요청의 400 필드 오류 키는 `venueName`이다. 공연 수정(PATCH)은 title만 받고 venueName/venueId가 와도 무시한다.
- 프론트: `venues.ts`·`VenuePicker` 삭제, 등록 화면 5단계에서 3단계로 축소, 홈·상세·타입 정리.
- 현재 테이블은 users·performance·performance_session·ticket 4개(+flyway_schema_history). 버려지는 정보는 venue.address·정식 등록 정보(status·verified_by·verified_at)·normalized_name뿐(로컬 데이터).
