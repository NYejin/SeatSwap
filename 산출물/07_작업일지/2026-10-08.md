# SeatSwap 작업일지

## 2026-10-08

### 결정 (CLAUDE.md '확정 전 기본안'에 대한 사용자 답변을 확정으로 반영)
1. **구역·좌석 단위**: 공연장 단위 구역 테이블을 두지 않는다. 공연마다 공연장 좌석을 그대로 쓰기도 바꿔 쓰기도 하므로 **공연 단위로 좌석**을 둔다. 구역 등록·자동완성은 좌석표 기능이 추가될 때 신경 쓸 부분이며, 지금은 사용자가 구역·열·번을 **텍스트로 직접 입력**한다. 공연장 관련 새 지시가 나오면 사용자에게 되묻는다
2. **열 표기**(숫자/문자)는 사용자에게 입력받는다
3. 직사각형 범위 선택 같은 고급 범위 입력과 펼침 상한 등은 좌석표 기능이 추가될 때 신경 쓸 부분(지금은 단순 텍스트 입력)
4. **회차**: 교환은 같은 공연 안에서 회차 구분 없이 가능, 매칭은 사용자가 원하는 회차끼리만(희망 회차 지정)
5. **추가금**: 상한 없음. 입력칸 대신 체크박스 [추가금 없음] [제시] (제시를 고를 때만 금액 입력)
6. **흐름**: 매칭 → 채팅 → 교환 후 각자 수락 → 교환 확정/완료
7. **교환 성사 후**: 마이페이지에 DB 기록만 남기고 관련 기능은 따로 추가하지 않는다. 사용자 신고 기능만 추후 추가
8. **같은 좌석 중복 등록**: 같은 회차·구역·열·번의 활성 티켓은 1개만 허용, 사용자당 활성 티켓 수 상한(예 20). 이미 등록된 좌석이면 안내 팝업/말풍선 + '내 티켓 인증' 링크. 인증 방식은 추후 결정(사진 업로드 → 관리자 수동 확인 예정)
9. **후보 노출**: 사용자가 교환을 원하는 회차를 우선, 회차 우선순위는 사용자가 설정
10. **범위 제한 없음**: 지정석·1매 제한을 두지 않는다(스탠딩 등도 텍스트 입력). 연석·3자 이상 순환 교환은 데이터 모델이 막지 않게 한다
11. **후기·신뢰도·신고**: 후기 기능은 만들지 않는다. 사용자 신고는 필수(교환 핵심 흐름 이후). 신뢰도 점수는 매칭에 쓰지 않고, 매칭 우선순위는 신뢰도가 아니라 사용자가 정한 우선순위를 따른다
- 이전 기본안 중 폐기된 것: 구역 자동완성, 요청당 300석 펼침 상한, 지정석·1매만, '후기·신뢰도 우선'
- CLAUDE.md '좌석표 트랙 동결' 항목에 "구역 등록·자동완성·범위 선택 UI는 좌석표 기능과 함께 후속" 추가

### 미확정 해석 (확인 필요 — CLAUDE.md 맨 아래 '확인 필요' 목록)
- 기존 `venue` 테이블(V1)은 유지하는 것으로 이해(구역 테이블만 두지 않음)
- 열·번 입력: 숫자는 범위(`3~5`)를 개별 좌석으로 펼치고, 문자 열은 개별 값으로만 받는 것으로 이해
- 추가금 '제시' 선택 시 낼 금액/받을 금액 구분(부호)이 필요한지, 두 사람 값의 합이 0 이상이면 성립하는 규칙을 그대로 쓰는지
- 매칭 생성 방식: 사용자 우선순위로 시스템이 상대를 자동 선택하는지, 후보 목록을 보여주고 사용자가 고르는지, 동순위 처리, 요청당 동시 진행 매칭 1개 여부
- '교환 후 각각 수락'의 의미(채팅에서 합의하고 실제 양도까지 끝낸 뒤 각자 '교환 완료' 수락?)와, 완료 시 Ticket 정보를 서로 바꿀지 vs 이력만 기록할지
- 신고 처리를 위한 최소 관리자 기능의 범위(신고 기능 착수 시 확인)

## 2차 답변 반영

### 결정 (사용자 2차 답변을 확정으로 반영)
1. **`venue` 테이블 삭제**: 공연장은 별도 테이블 없이 공연 정보에 텍스트로 둔다는 뜻으로 이해(공연장 검색·추가·정식 등록 개념 폐지). **코드·DB 반영(Venue 엔티티·컨트롤러·서비스·VenuePicker, `performance.venue_id` 제거, V2 마이그레이션)은 아직 시작하지 않음**
2. **추가금 부호 정정**: +는 내가 받을 금액, −는 내가 낼 수 있는 금액(입력 옆 안내 문구). 이전 기본안의 +/− 의미는 반대였으므로 정정
3. **매칭**: 시스템이 후보 목록을 띄우면 사용자가 골라 채팅 시작. 한 요청(티켓)에 채팅 여러 개 동시 가능, 동시 '예약'은 불가. **사용자 차단 기능**(차단 시 후보 제외·채팅 불가)을 새 요구로 기록. 취소 후 같은 상대와 재매칭 불가
4. **교환 완료**: 티켓팅 사이트에서 실제 양도까지 끝낸 뒤 각자 '교환 완료'. 마이페이지 '교환 이력'에 `(기존 자리) -> (바꾼 자리)` 형식(자리 정보 스냅샷 저장)
5. 열·번 입력 질문은 사용자가 이해하지 못해 **기본값**(숫자 `3~5`는 개별 좌석으로 펼침, `A열` 같은 문자 열은 하나씩 추가)으로 두고 쉬운 말로 재설명함. 이의 없으면 채택(미확정 표기 유지)

### 확인 필요 (CLAUDE.md '확인 필요' 절에 남김)
- venue 삭제의 범위: 공연 등록 화면의 공연장 입력 방식, 공연 목록의 공연장 필터 영향
- 추가금 성립 규칙: 두 값의 합 ≤ 0이면 성립(A +10,000과 B −10,000 성립, A +10,000과 B −5,000 불성립) — 사용자에게 예시로 확인 요청 중
- '예약' 단계 정의(채팅 중 양쪽이 '이 사람과 교환할게요'를 눌러 두 티켓을 잠그는 단계로 이해)와 티켓당 1개 규칙
- 취소 후 재매칭 불가 범위(자동 재매칭 불가인지, 차단과 별개인지)
- 완료 시 Ticket의 좌석·회차 정보를 서로 바꿀지(권장: 바꾸고 이력도 남김) vs 이력만 기록할지
- 한쪽만 완료하고 방치될 때 자동 만료 규칙(미답변, 설계 시 기본값 제안 예정)
- 신고 처리용 최소 관리자 기능 범위(신고 착수 시)
