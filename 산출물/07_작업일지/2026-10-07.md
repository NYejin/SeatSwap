# SeatSwap 작업일지

## 2026-10-07

### 결정
- **좌석맵 확보 방식 변경**: 링크 스크래핑으로는 얻을 수 없음. 멜론·YES24·티켓링크는 공개 페이지에 좌석맵이 없고(예매·보안문자 뒤), 인터파크는 robots.txt가 전면 금지.
  로그인·캡차 우회와 내부 API 조사는 하지 않음 → 정식 경로는 **사용자 이미지 업로드 / 이미지 주소 입력** (seatmap-service `/recognize`, `/recognize-url`)
- **이미지 보관**: 원본 이미지·주소는 저장하지 않고 인식한 좌표만 저장. 좌표는 원본 이미지 픽셀 기준, 화면은 SVG. 필요해지면 핫링크(A안)·서비스 보관(B안)으로 확장 (컬럼은 그때 Flyway로 추가)
- **좌석표 등록 흐름**: 공연장 정식 등록 전에는 사용자 이미지 인식 결과를 `DRAFT` 좌석표로 저장(공연장당 하나, 재사용·수정) →
  관리자가 공연장·공연을 정식 등록하면 `OFFICIAL`, 이후 그 공연장 공연에 자동 연결. 모든 수정은 로그(누가·언제·전후).
  악의적 수정은 신고·관리자 확인 시에만 제재(자동 제재 없음). 관리자는 DB에서 ADMIN 직접 부여로 시작
- **DRAFT 좌석표의 용도**: 확인용으로만 표시. 교환 매칭은 본인 좌석 정보 + 희망 좌석 범위로 하며, 좌표 기반 선택·매칭은 OFFICIAL에서만
- **오류 보정**: OFFICIAL은 정정 2건 이상 자동 반영(1건은 검토 대기), DRAFT는 수정 즉시 반영 + 로그
- **열 번호**: 통로를 건너도 번호를 이어씀(`aisleMode=continue` 기본). 실제와 다르면 사용자가 수정 요청·수정
- **링크 자동 입력 범위 축소**: 공개 페이지(JSON-LD·og)에서 제목·공연장·날짜 범위만 미리 채움. 회차 시각은 직접 입력. 자동 등록 없음, 인터파크 제외
- FR-02 정정 정책 문서: 관리자 정식 등록 + 수정 로그로 방향 결정, 상태는 '부분 결정'

## 이어서 진행한 작업(스키마 설계 ~ V2 구현)

### 결정 (스키마 설계 질문에 대한 사용자 답변)
- **DRAFT 좌석표는 공연장 안에서 구역(zone)별로 하나**(구역별 여러 개 허용). **OFFICIAL은 지금은 여러 개 허용하고 추후 공연장당 1개로 제한**(변경 예정)
- 공연장과 공연은 1:N. 공연 자체에는 정식 상태가 없고 `Venue.status`(UNVERIFIED/VERIFIED)만 둠
- 정식 등록은 좌석표 등록 시에만 가능 → 공연장 VERIFIED와 좌석표 OFFICIAL은 항상 함께 바뀜(정식 등록된 공연장에 좌석표가 없는 경우는 없음)
- `seat_map_layout.image_url` 삭제, `ticket.seatmap_id` NULL 허용: **티켓은 좌석표 없이 먼저 등록할 수 있고, 교환이 필요할 때 교환글을 등록하면서 DRAFT 좌석표를 업로드**
- 제재는 좌석표 수정·신고 정지(`SEATMAP_EDIT`)와 계정 정지(`ACCOUNT`) 두 종류. OFFICIAL 좌석표는 사용자 직접 수정 불가(정정 신고로만), 관리자는 직접 수정 가능. 제재는 신고나 관리자 확인이 있을 때만(자동 제재 없음)
- 회원탈퇴는 물리 삭제가 아니라 익명화(수정 로그·제재의 FK 유지)
- 악의적 수정 신고는 항상 로그(`abuse_report`)에 남고 관리자가 확인(관리자 페이지는 추후 제작 필요)
- 좌석맵 서비스 응답의 좌석에 안정적 식별자 `uid`(예 s0001) 추가(하위 호환). 검출 공간 순서 기준으로 결정적이며 행/열 보정·aisleMode와 무관. 수정 로그·정정 신고가 좌석을 가리키는 키

## 좌석표 등록·조회 구현과 실제 좌석표 시험

### 결정
- **좌석 표기 용어**: 한국 좌석 체계는 '열'(앞에서부터 1열, 뒤로 갈수록 커짐)과 '번'(한 열 안에서 왼쪽→오른쪽 1번, 2번…)이다. 화면 표기는 'N열 M번'(데이터 필드명 row/col은 그대로), 구역(층)이 둘 이상이면 '구역 N · M열 K번'. CLAUDE.md '좌석 표기(열/번)·구역(section)' 항목으로 반영
- 테스트용 임시 기능 TEMP-DRAFT-DELETE(`DELETE /api/seatmaps/{id}`, DRAFT만)를 두고 추후 제거 또는 주석 처리한다. `SEATMAP_DEV_DRAFT_DELETE`로 끌 수 있으며 코드에 'TODO: 임시 기능' 주석을 달았다(백엔드 컨트롤러·서비스·리포지토리·application.yml·docker-compose.yml, 프론트 api/seatmap.ts·SeatMapSelectPage·SeatMapUploadPage). CLAUDE.md에 한 줄 반영

## DRAFT 선점·스팸 대응(1차)

브랜치 `feature/draft-limits`(코드 변경 미커밋). 앞 절 '이슈'의 DRAFT 선점·스팸 정책 권장안 중 ①제한 ②삭제 권한을 먼저 구현했다.

### 결정
- 공연장당 좌석표(구역) 상한: 기본 20, 초과 시 422 `ZONE_LIMIT_REACHED`. ADMIN에도 적용
- 사용자당 24시간 내 등록: 기본 10건, 초과 시 429 `DAILY_LIMIT_REACHED`. ADMIN은 제외
- 설정: `SEATMAP_MAX_ZONES_PER_VENUE`, `SEATMAP_DAILY_LIMIT_PER_USER` (application.yml, docker-compose.yml)
- 삭제 권한: DRAFT는 작성자 본인 또는 ADMIN만 삭제(그 외 403). OFFICIAL은 삭제 불가, 티켓·신고가 참조하면 409. 작성자(created_by)가 NULL인 기존 행은 ADMIN만
- 임시 플래그 `SEATMAP_DEV_DRAFT_DELETE=true`인 동안은 로그인 사용자 누구나 삭제 가능(테스트용, 제거 예정). 플래그가 false면 작성자·관리자만 삭제하며, 이전에는 false일 때 404였다

### 구현
- 등록 검사 순서: 공연장 확인(404) -> 같은 구역 DRAFT 409 -> 구역 상한 422 -> 일일 제한 429 -> 동시성 제한(RATE_LIMITED 429 / BUSY 503) -> 인식. 모두 인식(비싼 호출) 전에 검사
- 삭제 검사 순서: 404 -> OFFICIAL 409 -> 권한 403 -> 참조 409. `ForbiddenException`과 핸들러 추가(403 `{"message"}`), `AuthUserPrincipal.isAdmin()`(필터가 요청마다 DB role로 만든 권한 기준)
- 응답에 `canDelete`(boolean) 추가: `GET /api/seatmaps/{id}`, `POST` 201 응답
- 프론트: `canDelete === true`일 때만 삭제 영역 표시, 삭제 403·404 문구 정리, 업로드 화면에서 `DAILY_LIMIT_REACHED`·`ZONE_LIMIT_REACHED` 문구('공연 상세로 돌아가기' 링크)
- 테스트: 백엔드 270건 통과, 프론트 tsc·build 통과

### 한계
- 삭제된 행은 일일 제한 집계에 잡히지 않아 삭제 후 재업로드로 우회할 수 있다 (V3 수정 로그에서 보완)
- count와 insert 사이에 락이 없어 동시 요청이 상한을 조금 넘길 수 있다
- 인덱스 없이 count 한다 (`seat_map_layout(created_by, created_at)` 인덱스는 V3 후보)

### 후속 과제
- [backend] DRAFT 수정 + 수정 로그(Flyway V3), 신고·제재(V4)
- [backend] V3에서 `seat_map_layout(created_by, created_at)` 인덱스 검토, 삭제 기록으로 일일 제한 우회 보완
- [backend] 임시 플래그 TEMP-DRAFT-DELETE 제거 시점 결정
- [docs] 병합 후 상태 갱신. 04 요구사항정의서(등록 제한·삭제 권한 FR)와 05 WBS 원본 반영 대기

## 좌석표 수정·정정 신고(V3)

브랜치 `feature/seatmap-edit-log`(코드 변경 미커밋, 미병합). 앞 절들의 후속 과제였던 Flyway V3(수정 로그·`seat_correction` 개편·`seat_count`)와 좌석표 번호 수정·정정 신고를 구현했다.

### 결정
- DRAFT 좌석표: 로그인한 누구나 즉시 수정(`USER_EDIT`), 모든 수정은 로그로 남긴다
- OFFICIAL 좌석표: 일반 사용자는 직접 수정할 수 없다(403). 관리자(ADMIN)만 직접 수정(`ADMIN_EDIT`)하고, 일반 사용자는 정정 신고로만 고친다
- 정정 신고 자동 반영: 같은 좌석·필드에 같은 정정값을 서로 다른 신고자 2명 이상이 접수하면 자동 반영(`CORRECTION_APPLIED`, 임계값은 설정, 최소 2로 고정). 1건이면 `PENDING`(검토 대기)
- 신고는 1신고 = 1행으로 두고 건수는 집계한다(`vote_count` 삭제). 같은 사용자의 중복 신고 방지는 대기(`PENDING`) 중인 신고에만 건다(종결 후 재신고 가능)
- 수정 로그는 append-only(수정·삭제하지 않음). 좌석은 seatmap-service의 안정 식별자 `seat_uid`로 가리킨다

### 구현
- Flyway V3(`V3__add_seatmap_revision_and_correction.sql`)
  - `seat_map_layout`: `seat_count` 추가(기존 행은 `JSON_LENGTH(seat_json)`으로 채움), 인덱스 `idx_seat_map_layout_created_by_at (created_by, created_at)`
  - `seat_map_revision`(수정 로그 헤더, append-only): `UK(seatmap_id, revision_no)`, `revision_no`는 `seat_map_layout.version`과 같은 값, `action_type`(RECOGNIZED/USER_EDIT/CORRECTION_APPLIED/ADMIN_EDIT/PROMOTED/REVERTED), `layout_status`, `actor_id`(NULL = 시스템 자동 반영), `reason`, `before_json`/`after_json`
  - `seat_map_revision_item`: 좌석·필드별 전후 값(`seat_uid`, `field_name`, `before_value`, `after_value`, `correction_id`)
  - `seat_correction` 개편: `vote_count` 삭제, `target_seat_uid`·`target_field`·`normalized_value`·`layout_version`·`created_at`·`reviewed_by`·`reviewed_at`·`review_note`·`applied_revision_id` 추가, `status`는 NOT NULL + CHECK(PENDING/APPLIED/REJECTED/SUPERSEDED). 중복 신고 방지는 `PENDING`일 때만 값이 있는 생성 컬럼 `pending_key` + `UNIQUE`
  - 파일 맨 앞에 가드: `seat_correction`에 행이 있으면 `SIGNAL`로 즉시 실패(아무것도 바꾸기 전에). 실패하면 `flyway repair`가 필요하다(백엔드 README 참고)
- API (`SeatMapController`, `SeatMapEditService`)
  - `PATCH /api/seatmaps/{id}/seats`: `expectedVersion`·`reason` 필수, `changes`는 `ROW_LABEL`/`COL_LABEL`. DRAFT는 로그인 사용자 누구나 즉시 반영, OFFICIAL은 ADMIN만(일반 사용자 403). 버전 충돌 409 `VERSION_CONFLICT`, 422 `UNKNOWN_SEAT`/`DUPLICATE_SEAT_NUMBER`/`NO_CHANGE`/`DUPLICATE_CHANGE`. 중복 번호는 변경한 좌석의 최종 (구역, 열, 번)만 검사
  - `POST /api/seatmaps/{id}/corrections`: OFFICIAL만(DRAFT는 409). 서로 다른 신고자 2명(설정, 최소 2) 이상이면 자동 반영(`CORRECTION_APPLIED`, actor NULL)하고 같은 좌석·필드의 다른 `PENDING`은 `SUPERSEDED`. 1건이면 `PENDING`. 반영하면 번호가 중복되는 경우 반영을 보류하고 `review_note`에 남긴다. 관리자 직접 수정도 같은 좌석·필드의 `PENDING`을 `SUPERSEDED`로 바꾼다. note는 저장하지 않는다
  - `GET /api/seatmaps/{id}/revisions`, `/revisions/{revisionId}`: ADMIN만
  - 수정·정정 반영은 좌석표 행을 `FOR UPDATE`로 잠근 뒤 한 트랜잭션에서 처리(`@Version`과 함께 사용)
  - 남용 방지: 사용자당 24시간 신고 30건(429 `CORRECTION_LIMIT_REACHED`, ADMIN 제외), 사용자당 `PENDING` 50건(429 `PENDING_LIMIT_REACHED`), 수정 요청 24시간 200건(429 `EDIT_LIMIT_REACHED`, ADMIN 제외), 락 대기 실패 503 `BUSY`. 설정 `SEATMAP_CORRECTION_THRESHOLD`·`SEATMAP_EDIT_DAILY_LIMIT`·`SEATMAP_CORRECTION_DAILY_LIMIT`·`SEATMAP_CORRECTION_PENDING_LIMIT`
  - 최초 인식 시 `RECOGNIZED` 로그 1건(reason '최초 인식', `before_json`/`after_json` NULL)
- 프론트
  - 번호 수정 모드: 직접 입력, 같은 열 번호 일괄 이동, 열 번호 변경. 변경 대기 목록·미리보기·사유 입력 후 한 번에 저장. 변경한 좌석은 점선 + 사선 빗금으로 표시
  - 오류 신고(OFFICIAL): 열·번을 순서대로 POST, 409는 건너뜀, note 입력 없음
  - 변경 이탈 경고는 `beforeunload` + `confirm`(BrowserRouter라 `useBlocker`를 쓸 수 없음)
  - 사용자 role은 `/users/me`로 화면을 나누고 서버가 최종 판정한다. 좌석표 목록에 'N석' 표시

### 검증
- 백엔드 테스트 320건 통과, 프론트 `tsc`·build 통과
- 임시 DB 3종에서 V3 적용·`validate` 통과: 빈 DB, 덤프 복사본, `seat_correction`에 행이 있는 복사본(가드 동작 확인)
- 동시성·제약은 임시 DB에서 수동 확인만 했다(Testcontainers 통합 테스트는 아직 없음)

### 한계
- 수정 로그가 있는 DRAFT 삭제 정책 미정: 현재는 최초 인식 로그(`RECOGNIZED`)만 있으면 native delete로 로그째 삭제하고, 수정·정정 로그가 있으면 409. '수정 로그 보존' 원칙과 충돌하며 soft delete는 V4 설계 후보다. 임시 플래그(`SEATMAP_DEV_DRAFT_DELETE`) 기본값 true는 운영 전 false로 바꿔야 한다
- 일일 한도 우회: 삭제된 행은 등록 한도에 잡히지 않는다
- 관리자의 `PENDING` 검토·반려 API가 없다(`REJECTED` 상태는 쓰이지 않음)
- `PROMOTED`/`REVERTED` 로그를 남기는 코드가 없다(관리자 정식 등록 서비스에서 남겨야 함)
- 수정 로그 조회 화면이 없다
- 정정 신고는 사실상 OFFICIAL 좌석표가 아직 없어 단위 테스트와 임시 DB로만 검증했다
- V3 적용 전 `seat_correction`에 행이 있으면 가드로 실패한다(이관 불가)

### 후속 과제
- [backend] 관리자 API·정식 등록 서비스(`PROMOTED` 로그), `PENDING` 검토·반려 API, `REVERTED` 처리

## 방향 전환 + 좌석표 트랙 정리

브랜치 `chore/remove-seatmap-track`(**미병합**, 코드 변경 미커밋). 서비스 구상을 자동 매칭으로 정리하고 좌석표 트랙을 동결하면서 관련 코드·설정·DB 마이그레이션을 걷어냈다. 단계마다 사용자 확인을 받고 진행했다.

### 결정
- **매칭 모델**: 사용자가 ①본인 좌석 1개 ②희망 좌석 범위(n개) ③추가금을 입력하면 시스템이 서로의 조건이 맞는 상대를 찾아 후보로 보여준다(자동 매칭). 점수화·랭킹·추천 알고리즘은 하지 않고, 후보 선택은 사용자가, 교환 확정은 양쪽 수락으로 한다
- 입력한 범위는 개별 좌석으로 펼쳐 저장한다(3열 3번, 3열 4번, …). 같은 공연의 다른 회차끼리도 허용하며 교환 범위는 공연(Performance) 단위다
- **좌석표 트랙 동결**: 좌석표 이미지 인식·좌석표 기반 선택은 후순위로 미룬다. 코드는 삭제하고 git 태그 `archive/seatmap-track-20261007`(master `d199b36`, 원격 푸시 완료)에 보관한다. 병합 후 삭제했던 `feature/seatmap-*` 브랜치는 따로 남아 있지 않아 이 태그가 유일한 보관본이다
- 당분간 좌석은 텍스트(구역·열·번)로 입력한다
- 백로그(사용자 재지시 전 시작하지 않음): V4 제재·신고, 관리자 API·관리자 페이지, 수정 로그 조회 화면, DRAFT 삭제 정책 등
- **확정 전 기본안**(CLAUDE.md '확정 전 기본안' 절, 사용자 확인 전이므로 확정이 아님)
  - 좌석 키는 (공연, 구역, 열, 번). 구역은 자동완성으로 고르게 한다
  - 범위는 그대로 저장하고 펼친 개별 좌석은 매칭 조인용 파생 데이터로 둔다(요청당 상한 300석)
  - 회차 조건은 희망 범위마다 둔다(같은 회차만 기본 / 모든 회차 / 선택한 회차)
  - 추가금은 부호 있는 금액 하나(희망 범위 행마다)이며 두 사람 값의 합이 0 이상이면 성립
  - 자동 매칭은 후보 제시까지, 확정은 양쪽 수락, 요청당 진행 중인 제안은 1개
  - 지정석 1매만(연석·3자 이상 순환 교환은 지금 구현하지 않음)
