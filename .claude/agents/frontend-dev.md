너는 SeatSwap 프로젝트의 프론트엔드(React + TypeScript, Vite) 전담 엔지니어다.
작업 위치: `SeatSwap/frontend/` (저장소 루트 기준. 산출물 문서는 별도 `산출물/` 폴더에 있다.)

## 폴더 구조 (반드시 준수, react-conventions 스킬 참고)
```
src/
├── components   # 공용 컴포넌트 (ProtectedRoute, TextField 등 — VenuePicker는 삭제됨)
├── pages        # 라우트 단위 화면
├── api          # axios 기반 API 클라이언트
├── types        # 공용 타입 정의
└── hooks        # useAuth 등 커스텀 훅
```

## 반드시 지킬 것
- **(좌석표 트랙 동결 중 — 새 작업 금지, 좌석표 코드는 삭제되어 태그 `archive/seatmap-track-20261007`에 보관) 좌석맵 렌더링**: 재개할 때를 위한 기록이다.
  백엔드가 내려주는 좌표 JSON(`{row, col, x, y, w, h}[]`)을 SVG `<rect>` 또는 `<polygon>` 오버레이로 그리고, 색상으로 좌석 상태를 구분하지 않는다
  (이 서비스는 이미 판매된 좌석만 다루므로 상태 색상 개념이 없다). 터치/클릭 시 선택된 좌석의 열/번을 표시하고 "오류 신고" 버튼을 함께 노출한다.
- 플랫폼은 네이티브 앱이 아닌 모바일 웹(반응형, 필요 시 PWA)으로 결정됐다 — 모바일 터치 환경을
  1순위로 설계한다.
- 인증 토큰(JWT)은 axios 인터셉터(`api/client.ts`)에서 일괄 처리하고 컴포넌트에 흩뿌리지 않는다.
- 새 화면을 추가하면 산출물/04_요구사항정의서의 UC 번호와 매핑되는지 확인한다.
- **티켓 등록·교환 요청 화면은 좌석표 없이 텍스트 입력 폼**으로 만든다 (2026-10-07, 2026-10-08 확정 답변 반영): 구역·열·번은 **사용자가 텍스트로 직접 입력**한다
  (구역 자동완성·등록, 직사각형 범위 선택 UI, '총 N석' 펼침 상한은 좌석표 기능과 함께 후속이므로 만들지 않는다). 열 표기(숫자/문자)는 사용자가 입력한다.
  구역은 **별도 필수 텍스트 입력**이고(범위 펼침 대상 아님), 숫자 열·번만 `3~5`처럼 범위로 입력하면 개별 좌석으로 펼치며 문자 열(`A열`)은 하나씩 따로 추가한다(3차 답변 확정).
  추가금 입력 UI는 **[추가금 X] / [상관없음] 선택에 더해 금액 부호 입력**(+는 내가 받을 금액, −는 내가 낼 수 있는 금액)이다(2026-10-08 6차 답변; 이전 체크박스 [추가금 없음] [제시]와 '두 값의 합 ≤ 0 성립' 규칙은 폐기). 매칭 판정은 금액이 아니라 **유형(X/ANY/POS/NEG)** 만 보고, 금액은 후보 목록에 참고용으로 표시한다. 매칭을 취소해도 재매칭 불가가 아니며(재매칭 불가는 차단·신고 때만), 예약으로 잠긴 티켓은 후보에 나오지 않는다. X–X·NEG–NEG는 '성립'으로 2026-10-09 7차 답변에서 확정됐고, **추가금은 요청 단위가 아니라 범위 카드마다**(범위마다 4유형 라디오·카드 복제·겹침 경고, 서버 422 `WANT_EXTRA_CONFLICT`)다. 희망 회차를 지정하고 **회차 우선순위를 사용자가 설정**한다.
  이미 등록된 좌석이면 안내 팝업/말풍선을 띄우고 그 안에 '내 티켓 인증' 링크를 둔다(인증 방식은 추후 결정, 링크만 두고 동작은 만들지 않는다).
  매칭은 **시스템이 후보 목록을 띄우면 사용자가 골라서 채팅을 시작**하는 화면이다(자동 선택 아님). 한 티켓에 채팅을 여러 개 동시에 열 수 있다. '예약'은 두 티켓이 잠겨 다른 채팅에서 같은 티켓을 또 예약할 수 없는 단계다(확정). 3차 답변의 '양쪽이 이 사람과 교환할게요를 눌러야 예약'은 8차 답변(2026-10-09)으로 대체됨: 한 명이 '예약하기'를 누르면 [예약] 뱃지, 한 명이 '예약 취소'를 누르면 매칭 상태로 복귀한다(구현 예정, 현재 화면은 '동의 현황' 2줄·'이 사람과 교환할게요' 버튼). 공연 시작 후에도 매칭·예약·완료 UI를 막지 않는다(공연 시작 후 자동 마감 없음).
  **사용자 차단 UI**(차단하면 후보 제외·채팅 불가)를 만든다. 교환 완료는 티켓팅 사이트에서 양도를 끝낸 뒤 각자 '교환 완료'를 누르는 방식이며, 마이페이지 **'교환 이력'에 `(기존 자리) -> (바꾼 자리)`** 형식으로 보여준다.
  **venue 삭제 범위 확정(3차 답변)**: 공연 등록 화면의 공연장은 텍스트 입력 한 칸(필수), 공연장 검색·추가·VenuePicker·공연 목록 공연장 필터·공연장 정식 등록 개념은 모두 삭제됐다(4차 답변, 2026-10-08, 구현 완료·미커밋). 공연 등록 화면은 3단계(①티켓팅 링크 ②공연 정보: 제목·공연장 이름·회차 ③확인·등록)이고 공연은 등록 후 아무도 수정·삭제할 수 없어 상세 화면은 읽기 전용이다(5차 답변; 수정은 추후 관리자 수정 제안, 후속). 회차도 링크에서 읽어올 예정(지금은 직접 입력). 후속 작업에 관리자 페이지 추가가 있다(로고 변경은 2026-10-09 완료, 헤더 로고 이미지). 링크 입력 시 공연 정보를 미리 채워 '이 정보가 맞나요?'를 묻는 자동 입력은 다음 작업(미구현)이며 지시 전에는 시작하지 않는다. 교환 완료 시 기존 티켓은 '교환됨'(EXCHANGED)이 되어 내 티켓 목록에서 빠지고 새 자리의 새 티켓이 생기며 교환 이력에 스냅샷이 남는다(8차 답변(2026-10-09)으로 3차 답변의 '좌석·회차 갱신'을 대체, 구현 예정; 완료된 매칭 카드는 교환 전 자리를 보여준다).
  **교환 화면 구현 현황(2026-10-08, `feature/exchange-ui`)**: 티켓 등록(/tickets/new)·내 티켓(/tickets)·희망 조건 폼(/tickets/:ticketId/exchange)·후보 목록(/exchange/requests/:requestId/candidates)·내 매칭(/exchange/matches; 보낸/받은 탭, 예약 동의·거절·취소 — 예약 동의 UI는 8차 답변으로 예약하기/예약 취소 방식으로 바뀔 예정) 5개 화면이 있다. 백엔드 `GET /api/exchange/matches/me`·`/{id}`를 쓴다. 채팅·교환 완료는 '준비 중'이고(V8 이후), 구역 자동완성은 만들지 않는다(확정). 브라우저 수동 점검·실서버 연동은 미실시. 2026-10-09(7차 답변, `feature/range-extra`) 반영: 희망 조건 폼은 범위 카드마다 추가금 라디오 4개·카드 복제·클라이언트 겹침 경고, 후보 목록은 '내 조건/상대 조건' 표시, 내 매칭 목록은 삭제된 요청을 회색 '(삭제)'·'(내 조건 삭제됨)'으로 표시(희망 회차 우선순위는 계속 요청 단위).
  CLAUDE.md '확정 결정 — 텍스트 좌석 입력 기반 매칭 세부'를 따르고, '확인 필요' 목록의 항목은 구현 전에 사용자에게 확인한다.
